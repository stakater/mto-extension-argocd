# Findings: what the sibling extension repos already solve

> [!IMPORTANT]
> **Superseded in places — this is the design record, not the current behaviour.**
>
> These documents were written before the chart existed and before it was run on
> a cluster. Building and testing it reversed several decisions recorded here.
> Where they disagree with the chart, the chart is right. Known reversals:
>
> | Recorded here | Actual |
> |---|---|
> | `sync.mode: revert` by default | `strict`, with two mandatory `ignoreFields` exemptions |
> | `strict` needs tov2 >= 0.0.6 | the webhook ships in v0.0.3 |
> | child TemplateInstances named `mto-argocd-<tenant>` | `mto-argocd-tenant-<tenant>`, so a Tenant named `parent` cannot collide with the parent |
> | fixed cluster-scoped RBAC names | release-scoped, or a second install fails |
> | bash render harness copied from openbao | Go, mirroring template-operator-v2's own function map |
> | a blank `argocd.namespace` renders zero children | it renders one per tenant, each of which then fails |
> | the IntegrationConfig read is fail-closed as written | it failed OPEN until fixed; absence is now an error |
>
> Live behaviour is in [../live-deployment.md](../live-deployment.md); upstream
> defects are in [../upstream-issues.md](../upstream-issues.md).

> pattern, instead of inventing. Feeds `PLAN-argocd-extension-extraction.md`; kept separate so the
> plan stays a plan.
> **Read on 2026-08-03:** `mto-extension-openbao` (branch `feat/pki-ca-trust-overlap`) and

## 1. Answers to the nine questions

| # | Question | Answer |
|---|---|---|
| 1 | Child TI naming | `openbao-config-mto-<tenant><suffix>`, suffixes **dot-separated** (`.eso`, `.certmanager`, `.trust`) because tenant names are RFC1123 labels and cannot contain dots — with a hyphen, tenant `x`'s eso TI collides with tenant `x-eso`'s core TI |
| 2 | Manager SA or per-TI SA? | **Manager SA.** Settled — see §2.1 |
| 3 | Does anyone use `Template.spec.outputs`? | Yes, on both parent and child. We are not first, and the parent pattern is better than ours — §2.4 |
| 4 | `values.schema.json` | Both hand-maintained charts ship one: JSON Schema draft-07, ~6 top-level properties, `required: []` |
| 5 | Why three charts? | Operator chart (auto-generated by helmify) · **bootstrap** chart (cluster-level: Templates, the one parent TI, RBAC) · **per-tenant** chart (pulled from OCI by tov2, never installed standalone) |
| 6 | Helm hook precedent for our migration Job | **None.** Zero `helm.sh/hook` annotations in any chart. We would be first |
| 7 | Chart test harness | **Exists and works** — §2.6 |
| 8 | How Grafana implements `Orphan` | **It does not.** Declared, never read — §3 |
| 9 | How Grafana implements `OnLabel` | **It does not.** Declared, never read — §3 |

## 2. The findings that matter most

These are the ones I did not think to ask for.

### 2.1 tov2 applies with its own manager ServiceAccount — question closed

`charts/openbao-config-mto-bootstrap/templates/00-rbac.yaml` creates two ClusterRoles and binds both
to `.Values.templateOperator.serviceAccountName` in `.Values.templateOperator.namespace`. There is no
per-TI ServiceAccount anywhere.

So installing an extension chart **widens template-operator-v2's own cluster-wide permissions**.
OpenBao ships this in production and accepted the trade. **We are not accepting it** — most of it is
avoidable at no cost, and the plan's §4.6 now specifies a least-privilege split instead:

- `discoverOwnedResources` ([templateinstance_controller.go:500-507](/Users/ayeshafateh/Documents/Stakater/GitHub/template-operator-v2/internal/controller/templateinstance_controller.go#L500)) LISTs cluster-wide with no namespace option, so `list`/`watch` must be cluster-scoped — but they are **read-only**.
- Every mutating verb on `appprojects` moves to a **RoleBinding in the argo namespace**, because that is the only namespace AppProjects ever occupy. Cluster-wide *write* — the thing an attacker actually wants — disappears.
- `integrationconfigs` and child `templateinstances` writes likewise become namespace-scoped; `tenants` and `namespaces` stay cluster-wide reads because both kinds are cluster-scoped and we LIST all of them.

The residual risk is irreducible from a chart: the identity is shared, so tov2 still holds argo-namespace
write on behalf of every TemplateInstance in the cluster. The real fix is a per-apply identity in tov2 —
filed as **TOV2-2** (impersonate a `Template.spec.serviceAccountName`), which would fix this for every
extension at once rather than just ours.

### 2.2 Revoking RBAC on teardown deadlocks the cluster — the most transferable lesson

Quoting the reasoning in `00-rbac.yaml` (paraphrased): turning an integration off in one `helm upgrade`
both removes the child Template and rewrites the ClusterRole. The TI then enters deletion, and its
finalizer must list the owned objects, patch its own finalizer off each one, and delete them. If the
upgrade already revoked `list`/`patch`/`delete`, that finalizer fails `Forbidden` **forever**: the TI
is stuck `Terminating`, the child Template cannot finalize while a TI references it, and every object
the slice created is orphaned with a finalizer nothing will remove. Recovery needs a hand-applied
ClusterRole.

Their rule: **grant the reap verbs (`get`/`list`/`watch`/`update`/`patch`/`delete`) unconditionally,
and gate only `create` behind the feature toggle.**

Directly applicable to us. Our §4.6 RBAC block grants all verbs on `argoproj.io/appprojects` in one
list. If we ever add a toggle — and `scaffoldingMode: Never` is exactly such a toggle — the same
deadlock applies. This is also the same failure class as the finalizer-ordering hazard already in the
plan's Phase 3, from a different direction.

### 2.3 tov2 dry-runs the whole render, so co-rendered RBAC cross-references cannot work

Also from `00-rbac.yaml`: a `Role` rendered next to its `RoleBinding` does not exist when Kubernetes
validates the `roleRef`, because the dry-run never persists — so the binding is rejected and **the
render can never apply**. Their fix is to define the ClusterRole in the Helm chart and only bind it
from the render.

We already ship RBAC via Helm rather than the render, so we are accidentally correct. Worth writing
down as a rule: anything whose admission check references another object cannot be co-rendered with it.

### 2.4 The parent TI can aggregate every child's health — better than what we planned

`templates/30-parent-template.yaml:62` declares on the **parent**:

```yaml
outputs:
  - name: tenants
    fromAll:
      apiVersion: templates.v2.stakater.com/v2alpha1
      kind: TemplateInstance
      namespace: <operatorNamespace>
    keyTemplate: "{.metadata.name}"
    fields:
      - { name: tiApplied,           jsonPath: "{.status.conditions[?(@.type=='Applied')].status}" }
      - { name: tiReady,             jsonPath: "{.status.conditions[?(@.type=='Ready')].status}" }
      - { name: tiSynced,            jsonPath: "{.status.conditions[?(@.type=='Synced')].status}" }
      - { name: tiMatchedNamespaces, jsonPath: "{.status.matchedNamespaces}" }
```

Because the parent's rendered output *is* the set of child TIs, `fromAll` over `TemplateInstance`
gives per-tenant health from one object:

```bash
kubectl -n <opNs> get ti openbao-config-mto-parent -o jsonpath='{.status.outputs}'
```

Our §4.5 proposes `kubectl get templateinstances -l <chart label>`, which needs a label scheme and
still prints one row per tenant with no condition detail. **Copy the aggregator.** It also partly
answers the "did per-tenant status really survive the move?" objection: the aggregate view is
arguably better than the `Extensions` CR ever gave.

Child-level outputs use the same `fromAll` + `keyTemplate` + per-field `jsonPath` shape we designed,
so that half is confirmed. One caveat carried in their comment: **status size scales with per-tenant
cardinality** — they explicitly say to drop an output if tenants run O(1000) of the underlying object.
Ours is one AppProject per tenant, so we are safe, but the parent aggregator grows with tenant count.

### 2.5 A child TI can carry `valueFrom`, not only literal strings — corrects the plan

`files/parent-gotemplate.tpl:103-120` emits child parameters like this:

```yaml
- name: serviceAccounts
  valueFrom:
    objectFieldRef:
      apiVersion: v1
      kind: ServiceAccount
      jsonPath: .items
      namespaceSelector:
        matchLabels:
          <tenantLabel>: <tenant>
```

So the parent → child channel is **not** string-only. Precisely:

- values the parent **computes** must go through `value:` and therefore through a string (our JSON-encoding rule in §3.12 stands for the filtered namespace list);
- values the child can **look up for itself** can be passed as a `valueFrom` block and arrive structured.

This is also exactly why OpenBao hits `NamespaceSelectorMatchedZero` and needs its `$hasNs` guard —
its children resolve their own namespace-scoped params. Our parent-side resolution avoids that, which
the plan already argues; the new information is that the child-side option exists at all, and could be
used for the IntegrationConfig-derived resource lists if the string round-trip proves awkward.

### 2.6 There is a working chart-render test harness to copy

- `Makefile:510-517` — `helm-lint` runs `helm lint --strict` on both hand-maintained charts; `helm-render-test` runs `hack/chart-render-tests.sh` (needs `helm` + `yq`).
- Golden fixtures live in `hack/render-fixtures/golden-all.yaml`.
- `.github/workflows/pull_request.yaml` has a dedicated `chart-tests` job: *"Charts only — no Go build, so no private-module auth needed."* Its ignore list carries the comment *"`hack/` is deliberately not ignored — it holds the chart render tests and their golden fixtures."*
- The harness checks four properties, per the Makefile help: **golden, disjoint, union, purity**.

Our §7 leans entirely on `helm template` golden files and budgets nothing for building that
infrastructure. It already exists. Copy the script and the CI job shape — and note the no-Go-build
point, which matters because a chart-only repo has no private-module auth to configure.

### 2.7 `sync.mode` conventions, and what `strict` costs

`values.yaml:114-122` documents all three modes and defaults to **`revert`**, not `off`:

- `off` — apply once per re-render; out-of-band edits persist
- `revert` — watch every rendered resource and re-apply on drift
- `strict` — revert plus an admission webhook blocking third-party UPDATE/DELETE

There is an `ignoreFields` list (dot notation, `[*]` wildcard), with the note: **"strict needs at
least `metadata.finalizers`"**. Their `Chart.yaml` pins the requirement as tov2 `>= 0.0.5` for
`namespaceSelector`, `>= 0.0.6` for `sync.mode=strict`.

Two consequences for us. Defaulting to `revert` gives AppProject drift correction for free, which the
plan already lists as a behaviour improvement — so it is a values default, not a design question. And
if we adopt `strict` (the plan calls it attractive), we **must** exempt `metadata.finalizers`, which is
also strong evidence for the answer to our spike question "does strict block tov2's own cleanup?" —
it interferes with finalizer writes unless exempted.

## 3. Grafana is not a model to copy

I previously recommended borrowing two things from Grafana. Both turn out to be **declared but never
read**:

| Symbol | Where declared | Where read |
|---|---|---|
| `ScaffoldingModeOnLabel` | `api/v1alpha1/enum_types.go:135` | nowhere |
| `DeletionPolicyOrphan` | `api/v1alpha1/enum_types.go:117` | nowhere |

`ScaffoldingSpec` (`grafana_types.go:233-243`) is `{mode, annotations map[string]string}` — there is no
`labels` map, so `OnLabel` has nothing to match against. `Spec.DeletionPolicy` is referenced exactly
once, at `operatorconfig.go:123-124`, only to default it to `Delete`; nothing branches on `Orphan`.

Both are in the CRD schema, so **a user can set them today and silently get the other behaviour**.
That is a bug worth reporting to that repo, independent of our work.

What survives for us: the *vocabulary* is still the right thing to reuse — `scaffolding.mode` with
`Always`/`OnLabel`/`OnAnnotation`/`Never`, and `Orphan` as the word for retain — because it is already
in a shipped CRD and consistency is cheap. But there is **no implementation to learn from**, so we
should not describe either as "as Grafana does it", and we must implement `OnLabel` ourselves if we
offer it.

Grafana also ships **no chart content at all** — `charts/charts/` is empty, the chart is helmify-
generated at build time. So it is not a source for chart layout, values conventions, or tests.

## 4. What to do

**Copy:**

1. The parent-TI aggregator output (§2.4) — replaces our per-child `kubectl -l` plan.
2. `hack/chart-render-tests.sh` + the `chart-tests` CI job + `golden-all.yaml` fixture layout (§2.6).
3. `values.schema.json`, draft-07, and enforce the `scaffolding.mode` enum there.
4. The RBAC split: reap verbs unconditional, `create` gated (§2.2).
5. `sync.mode: revert` as the default; `ignoreFields` including `metadata.finalizers` if `strict`.
6. Dot-separated suffixes **if** we ever emit more than one TI per tenant (§1, row 1). One per tenant
   today, so `mto-argocd-<tenant>` is safe — record the constraint so a future slice does not break it.
7. The `Chart.yaml` description convention: state what the chart is, that it is pulled by tov2 rather
   than installed standalone where true, and pin minimum tov2 / MTO versions.

**Differ deliberately, and accept the risk:**

- **Three `objectFieldRef` parameters on one parent TI.** OpenBao's parent has exactly **one**
  (`tenants`, `jsonPath: .items`). Our design wants Tenants + Namespaces + IntegrationConfig. Nobody
  has run that, so spike question "do all three register watches?" stays open and is now the *only*
  materially unproven part of the parent design.
- **Parent-side namespace resolution.** Deliberate, and the plan argues it well; the new supporting
  evidence is §2.5 — child-side resolution is exactly what forces OpenBao's `$hasNs` guard.
- **A Helm hook Job** for the ownerRef strip. No precedent in the family (§1, row 6), so budget for
  getting the SA and RBAC right from scratch.

**Report upstream:** the two dead enum values in Grafana (§3).
