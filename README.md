# mto-extension-argocd

Give every Multi Tenant Operator tenant its own ArgoCD `AppProject` — scoped to
that tenant's namespaces, with owner, edit and view roles — from an annotation
on the `Tenant`.

A Helm chart, rendered by [template-operator-v2][tov2]. No operator, no image,
no OLM bundle. It replaces `ExtensionsArgoCDReconciler` and the `Extensions`
CRD in [multi-tenant-operator][mto].

## What you get

Annotate a `Tenant`:

```yaml
apiVersion: tenantoperator.stakater.com/v1beta3
kind: Tenant
metadata:
  name: acme
  annotations:
    argocd.tenantoperator.stakater.com/enabled: "true"
spec:
  accessControl:
    owners:
      groups: [acme-admins]
      users:  [alice@acme.example]
```

and an `AppProject` appears, scoped to that tenant:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: acme
  namespace: openshift-gitops
spec:
  description: Managed by mto-extension-argocd
  destinations:                        # the tenant's namespaces, minus privileged ones;
    - namespace: acme-dev              # never the ArgoCD namespace (see Security defaults)
      server: https://kubernetes.default.svc
    - namespace: acme-prod
      server: https://kubernetes.default.svc
  roles:
    - name: acme-owner
      policies:                        # least privilege, see Security defaults
        - p, proj:acme:acme-owner, applications, *, acme/*, allow
        - p, proj:acme:acme-owner, applicationsets, *, acme/*, allow
        - p, proj:acme:acme-owner, logs, get, acme/*, allow
        - p, proj:acme:acme-owner, repositories, *, acme/*, allow
        - p, proj:acme:acme-owner, clusters, get, acme/*, allow
      groups:
        - acme-owner-group-c2ef09      # generated by MTO, only on OpenShift
        - acme-admins                  # the tenant's groups
        - alice@acme.example           # and its users — see Before production
    # acme-edit: get, sync, update on applications, get on the rest
    # acme-view: get on everything
```

Remove the annotation and the chart stops managing the `AppProject` — whether
it is kept or deleted depends on your template-operator-v2 version, see
[What deletes an AppProject](#what-deletes-an-appproject).

## Quick start

**1. Install.** `argocd.namespace` is required and has no default:

```bash
helm install mto-extension-argocd ./charts/mto-extension-argocd \
  --namespace multi-tenant-operator \
  --set argocd.namespace=openshift-gitops
```

Nothing is scaffolded yet — `scaffolding.mode` defaults to `OnAnnotation`.

**2. Opt a tenant in.** The value must be exactly `"true"`; `"True"`, `"yes"`
and `"1"` all read as opted *out*, deliberately.

```bash
kubectl annotate tenant acme argocd.tenantoperator.stakater.com/enabled=true
```

**3. Check it.** One row per opted-in tenant:

```bash
kubectl get templateinstances.templates.v2.stakater.com \
  -n multi-tenant-operator -l templates.v2.stakater.com/instance \
  -o custom-columns='TENANT:.spec.parameters[?(@.name=="tenant")].value,\
READY:.status.conditions[?(@.type=="Ready")].status'
```

```text
TENANT   READY
acme     True
```

A complete, commented pair of examples lives in
[examples/tenant.yaml](examples/tenant.yaml) and
[examples/values-production.yaml](examples/values-production.yaml).

## How it works

The chart runs no controller of its own. Three template-operator-v2 objects
are the whole mechanism:

| Object | Role |
|---|---|
| `Template/mto-argocd-parent` | Ranges over every `Tenant`, emits one child per tenant that passes the scaffolding filter |
| `Template/mto-argocd-child` | Renders one tenant's `AppProject` |
| `TemplateInstance/mto-argocd-parent` | The only `TemplateInstance` in git |

With `rbac.create: true`, the default, the chart also installs eight RBAC
objects — two ClusterRoles, one ClusterRoleBinding, two Roles and three
RoleBindings (one of them the AppProject-write binding in `argocd.namespace`,
which is what confines mutation to that namespace) — granting
template-operator-v2 the least privilege those three need
([00-rbac.yaml](charts/mto-extension-argocd/templates/00-rbac.yaml)).

```text
Tenant ───────────┐
Namespace ────────┼──▶ parent TemplateInstance ──▶ one child per tenant ──▶ one AppProject per tenant
IntegrationConfig ┘
```

The parent takes exactly three inputs — a cluster-wide `LIST` of Tenants, a
cluster-wide `LIST` of Namespaces, and one namespaced `GET` of the
`IntegrationConfig`. That is **three watches regardless of tenant count**, and
a namespace event affecting one tenant rewrites only that tenant's child.

From the `IntegrationConfig` it reads `accessControl.privileged` only:
privileged namespaces are excluded from every tenant's `destinations`, and
privileged groups are added to every role. The match is an **unanchored**
regex, matching the controller this replaces — so a pattern of `openshift` also
excludes `my-openshift-tools`.

`integrations.argocd.{namespace,clusterResourceWhitelist,namespaceResourceBlacklist}`
are **deprecated** and no longer read; those values move into chart values.
`accessControl.privileged` is unaffected.

## Configuration

### Chart values

Full reference with rationale in
[values.yaml](charts/mto-extension-argocd/values.yaml). The ones that matter:

| Value | Default | |
|---|---|---|
| `argocd.namespace` | — | **Required.** Where AppProjects are created |
| `scaffolding.mode` | `OnAnnotation` | `Always`, `OnLabel`, `OnAnnotation`, `Never` |
| `argocd.sourceRepos.pattern` | `[]` | Per-tenant repo patterns, one sourceRepos entry each; `{{ tenant }}` is expanded |
| `argocd.clusterResourceWhitelist` | `[]` | Cluster-scoped kinds tenants may manage |
| `argocd.namespaceResourceBlacklist` | `[]` | Namespaced kinds they may not |
| `sync.mode` | `strict` | Drift protection — see [Operations](#operations) |
| `argocd.allowControlPlaneDestination` | `false` | The legacy, unsafe shape — see [Security defaults](#security-defaults) |
| `roles.profile` | `leastPrivilege` | Or `extensionsCompatible`, the legacy shape |
| `roles.exec.enabled` / `roles.clusters.enabled` | `false` | Owner-only exec, cluster writes |

### Per-tenant overrides

Four settings can be overridden per tenant, as annotations under
`argocd.tenantoperator.stakater.com/`:

| Annotation | Overrides | Format |
|---|---|---|
| `source-repos` | `argocd.sourceRepos.pattern` | JSON array of strings |
| `cluster-resource-whitelist` | `argocd.clusterResourceWhitelist` | JSON array of `{group, kind}` |
| `namespace-resource-blacklist` | `argocd.namespaceResourceBlacklist` | JSON array of `{group, kind}` |
| `on-delete-purge` | `onDeletePurgeAppProject` | `"true"` or `"false"` |

An **absent** annotation inherits the chart default. An explicit `[]`
**overrides with empty** — a different thing, which is why the annotation's
value is passed to the child verbatim rather than parsed by the parent.
Malformed JSON fails that tenant's child and nothing else; it never falls back
to the default, because applies are server-side and a fallback would *strip*
the field from a live AppProject.

`sourceRepos` has no shareable default — one org-wide value would let every
tenant deploy from every other tenant's repos. The only safe shared form is a
list of patterns templated on the tenant name, one `sourceRepos` entry each:

```yaml
argocd:
  sourceRepos:
    pattern:
      - https://github.com/acme/{{ tenant }}-gitops
      - https://github.com/acme/{{ tenant }}-charts
```

Tenant `team-a` then gets `https://github.com/acme/team-a-gitops` and
`https://github.com/acme/team-a-charts`. Only `{{ tenant }}` and `{{tenant}}`
are substituted; any other placeholder, a plain string instead of a list, or
an empty entry is refused at install time rather than shipped into a live
AppProject.

## Security defaults

Since chart **0.2.0** (#6, #7). Earlier versions — and the
`ExtensionsArgoCDReconciler` they reproduce — had both problems below.

**The ArgoCD namespace is never a tenant destination.** An Application in the
control-plane namespace may reference *any* AppProject, and the application
controller that syncs into it is cluster-admin, so a tenant able to deploy
there can create Applications, AppProjects or repository and cluster Secrets
for every project — ArgoCD admin
([ArgoCD docs](https://argo-cd.readthedocs.io/en/stable/operator-manual/app-any-namespace/)).
The AppProject does not need it: it lives in the ArgoCD namespace whatever
`destinations` says. `argocd.allowControlPlaneDestination: true` restores the
legacy shape exactly — **unsafe**, for a migration only.

**Roles are least privilege** (`roles.profile: leastPrivilege`):

| Role | applications | applicationsets | logs | repositories | clusters | exec |
|---|---|---|---|---|---|---|
| owner | `*` | `*` | `get` | `*` | `get` (`*` with `roles.clusters.enabled`) | — (`create` with `roles.exec.enabled`) |
| edit | `get`, `sync`, `update`, `update/*`, `action/*` | `get` | `get` | `get` | `get` | — |
| view | `get` | `get` | `get` | `get` | `get` | — |

Edit cannot create, delete or override Applications. ArgoCD's web terminal runs
as the argocd-server ServiceAccount, outside the tenant's own RBAC and audit
trail, so `exec` is off unless you turn it on (owner only).
`roles.profile: extensionsCompatible` restores the legacy six-line `*`/`get`
shape — for a migration only. Consider also setting
`application.sync.requireOverridePrivilegeForRevisionSync` in ArgoCD (3.2+).

**Upgrading from 0.1.0.** Every managed AppProject changes on the next render:
the ArgoCD namespace leaves `destinations`, and the roles narrow. Applications
that deploy *into* the ArgoCD namespace stop syncing; move them out of the
control plane first, or set both compatibility values, upgrade, migrate, and
remove them.

## Applications in the tenant's own namespace

Off by default (#9). With it, tenants create their Applications in their own
namespace instead of the ArgoCD control plane, whose write access is ArgoCD
admin:

```yaml
argocd:
  sourceNamespaces:
    enabled: true
    pattern: "{{ tenant }}-argocd"   # the default
```

Every AppProject then carries `sourceNamespaces: [<tenant>-argocd]`, but only
once that namespace exists and carries the tenant's label, like a destination.
Anyone who can write an Application in a source namespace can use the
AppProject, so it is never a namespace that belongs to someone else.

The pattern must contain `{{ tenant }}` and expand to a plain namespace name.
ArgoCD reads a glob there, and `{{ tenant }}*` for `acme` would also match
`acme-corp-argocd`; both are refused at install time. A pattern that expands
to the ArgoCD namespace, or to a privileged namespace, fails that tenant's
child and no other.

Kubernetes RBAC on that namespace decides who creates and deletes
Applications there: a tenant member with `edit` in it can `kubectl apply` one.
The project roles (edit cannot create or delete, see
[Security defaults](#security-defaults)) govern only the ArgoCD UI and API.

Applications in any namespace is
[stable in ArgoCD](https://argo-cd.readthedocs.io/en/stable/operator-manual/app-any-namespace/)
and needs two gates; this chart sets only the second:

1. **ArgoCD watches the namespaces.** Upstream: `application.namespaces:
   "*-argocd"` in `argocd-cmd-params-cm`, then restart argocd-server and the
   application controller; argocd-server also needs the cluster RBAC described
   in the ArgoCD docs. OpenShift GitOps 1.13+: `ArgoCD.spec.sourceNamespaces`
   (globs accepted) on the cluster-scoped instance.
1. **The AppProject allows them** — `sourceNamespaces`, rendered here.

The `<tenant>-argocd` namespace itself comes from the Multi-Tenant Operator,
for example `namespaces.withTenantPrefix: [argocd]` on the Tenant. Keep it
separate from workload namespaces: on OpenShift GitOps a namespace cannot be
both `managed-by` an instance and a source namespace without custom roles.
The tenant's existing `<tenant>/*` role policies already cover Applications
there; 3-segment policies (`<project>/<namespace>/<app>`) need ArgoCD 3.4.4 or
later.

## Sync impersonation

Off by default (#15). Without it every sync runs as ArgoCD's application
controller, which upstream ships with a `*/*/*` ClusterRole. With it, ArgoCD
syncs as a ServiceAccount in the destination namespace, so a sync can only do
what the tenant could do itself:

```yaml
argocd:
  impersonation:
    enabled: true
    serviceAccount: argocd-deployer   # the default
```

Every AppProject then carries one `destinationServiceAccounts` entry per tenant
namespace, `defaultServiceAccount: argocd-deployer`. There is deliberately no
catch-all entry, unlike the upstream example: a destination without an entry
fails the sync instead of falling back to the controller. The ArgoCD namespace
never gets an entry.

Also needed, outside this chart:

1. **ArgoCD 3.5 or later**, where
   [impersonation](https://argo-cd.readthedocs.io/en/stable/operator-manual/app-sync-using-impersonation/)
   is beta (alpha before) and also covers server operations. Enable it with
   `application.sync.impersonation.enabled: "true"` in `argocd-cm`; on
   OpenShift GitOps, through `ArgoCD.spec.extraConfig`.
1. **The ServiceAccount in every tenant namespace**, bound to the namespace's
   `edit` ClusterRole. A Multi-Tenant Operator template does it once for every
   tenant:

   ```yaml
   apiVersion: tenantoperator.stakater.com/v1alpha1
   kind: Template
   metadata:
     name: argocd-deployer
   resources:
     manifests:
       - apiVersion: v1
         kind: ServiceAccount
         metadata:
           name: argocd-deployer
       - apiVersion: rbac.authorization.k8s.io/v1
         kind: RoleBinding
         metadata:
           name: argocd-deployer-edit
         roleRef:
           apiGroup: rbac.authorization.k8s.io
           kind: ClusterRole
           name: edit
         subjects:
           - kind: ServiceAccount
             name: argocd-deployer
   ```

   Apply it to every tenant namespace with a `TemplateGroupInstance` whose
   selector matches the `stakater.com/tenant` label.

1. **A reduced controller ClusterRole** for real damage limitation. Otherwise
   impersonation enforces tenant boundaries at sync time, but the controller
   still holds cluster-admin.

ArgoCD picks the account by the Application's destination namespace, and the
template above grants it `edit` in that namespace only. Two kinds of
Application therefore stop syncing: one that carries a cluster-scoped kind from
`clusterResourceWhitelist`, such as a `Namespace`, and one whose manifests put
objects into another namespace. Grant those rights to the deployer
deliberately, or keep such Applications out of tenant projects.

## Groups named by pattern

By default (`identity.mode: accessControl`) each role's groups are the
Tenant's owners, editors and viewers, as the old controller rendered them. The
other Stakater extensions take access from identity-provider groups named by
pattern instead, and so can this chart (#10):

```yaml
identity:
  mode: groupPattern                            # or both, while moving over
  groupPattern: "tenant-{{ tenant }}-{{ tier }}" # the default
```

Tenant `acme` then gets `tenant-acme-owners`, `tenant-acme-editors` and
`tenant-acme-viewers`. The MTO-generated group and the privileged groups are
kept in every mode. `both` appends the pattern group to the Tenant's lists.

It matters most on OpenShift with external OIDC (4.20+), where the
MTO-generated OpenShift group never reaches ArgoCD, and wherever user entries
would otherwise need `scopes: [groups, email]`. The pattern must contain both
placeholders. Use a prefix your identity provider controls, and never a name a
local ArgoCD user has: an SSO group named like a local user inherits that
user's roles.

## Before production

Four ways to end up with something that looks correct and isn't.

**Seed the resource lists from the IntegrationConfig.**
`clusterResourceWhitelist` and `namespaceResourceBlacklist` moved out of
`integrations.argocd`. Forget them and every tenant's AppProject silently loses
both lists.

**Set `sourceRepos`.** An AppProject with none permits *no* repository, so
ArgoCD rejects every Application with `application repo ... is not permitted in
project`. This is true of the old controller's output too — creating the
AppProject is not the same as making the tenant able to deploy.

**List real groups *and* users.** `roles[].groups` gets the MTO-generated group
first, but MTO only creates it when the tenant-operator runs with
`PLATFORM_TYPE=Openshift`. That is an environment variable, not a detected
value, so it can read `Kubernetes` on an OpenShift cluster with nothing to
indicate it — and a tenant whose owners are only that group gets an AppProject
granting access to nobody.

**Let ArgoCD match users by email.** The chart adds the tenant's users to
`roles[].groups`, for example `alice@example.com`. ArgoCD compares that list
with the login token's user ID and with the claims named in `argocd-rbac-cm`
`scopes`, which defaults to `[groups]`. Behind Dex the user ID is an opaque
value, not an email, so with the default the user entries grant nothing. Add
the claim that holds the user name the Tenant uses — usually `email`:

```yaml
# argocd-rbac-cm, in the ArgoCD namespace
data:
  scopes: '[groups, email]'
```

ArgoCD reloads it without a restart. With Dex in front of OpenShift, `email`
carries the OpenShift user name, which is the name MTO Tenants use. Two
consequences: the setting is global, so email entries in `policy.csv` start to
match too, and a user in a project role can create tokens for that role.
ArgoCD trusts the claim as it is, so only include a claim that users cannot
change themselves in the identity provider. Verified on ArgoCD 3.4.6 with Dex:
the user had no access with the default `scopes` and full role access with
`[groups, email]`.

## Operations

### Drift protection

`sync.mode` defaults to `strict`, so a managed AppProject cannot be hand-edited
or deleted — tov2's admission webhook refuses both. Under the looser `revert`,
a deleted AppProject wedges in `Terminating` forever while its TemplateInstance
still reports healthy.

`argocd proj role create-token` and `delete-token` work: ArgoCD writes tokens
into `spec.roles[].jwtTokens`, which the chart exempts. The next re-render
removes that spec copy, because `roles` is applied as one list, but the token
stays valid: ArgoCD checks project tokens against `status.jwtTokensByRole`,
which template-operator-v2 does not touch. Verified on ArgoCD 3.4.6, including
revocation.

### What deletes an AppProject

> [!WARNING]
> On template-operator-v2 **v0.0.6 and earlier**, the default configuration
> **deletes** the AppProject when you remove a tenant's opt-in annotation,
> narrow `scaffolding.mode`, delete the `Tenant`, or run `helm uninstall`.
> `onDeletePurgeAppProject: false` has no effect there. Use v0.0.7 or later to
> keep AppProjects.

Why: tov2 owns every object a child TemplateInstance renders. When the parent
stops rendering a child, tov2 deletes the child and cleans up its objects. With
`onDeletePurgeAppProject: false` the chart marks each AppProject
`templates.v2.stakater.com/deletion-policy: Orphan`. v0.0.7 and later honour
the mark and *release* the AppProject: the object stays, without the tov2
finalizer and labels, and ArgoCD keeps using it. v0.0.6 and earlier ignore the
mark and delete the object.

| Trigger | v0.0.7+, purge off (default) | v0.0.7+, purge on | v0.0.6 and earlier |
|---|---|---|---|
| The tenant's opt-in annotation is removed | released | deleted | deleted |
| `scaffolding.mode` is narrowed | released, for every tenant the new mode excludes | deleted | deleted |
| The `Tenant` is deleted or renamed | released | deleted | deleted |
| `helm uninstall`, or the parent TemplateInstance is deleted | released, for every tenant | deleted | deleted |
| A chart change renames the child TemplateInstance | released | deleted | deleted |

"Purge on" is `onDeletePurgeAppProject: true`, or the `on-delete-purge`
annotation on one Tenant. A rename of the child TemplateInstance is a breaking
chart change and needs a release note. To keep one tenant's AppProject on
v0.0.6 and earlier, see [docs/rollback.md](docs/rollback.md). `make e2e-kind`
reports which behaviour your operator has.

These do **not** delete an AppProject:

| Situation | What happens |
|---|---|
| A malformed override annotation on a Tenant | that tenant's child fails; its AppProject does not change |
| A tenant loses all its namespaces | it keeps its AppProject, with the ArgoCD namespace as the only destination |
| The parent cannot render, for example `integrationConfig.name` is wrong | children and AppProjects stay; tov2 keeps the last rendered set, so a broken `IntegrationConfig` cannot wipe the fleet |
| A chart upgrade or a values change | each AppProject is updated in place; the UID does not change |

### Checking fleet health

One object answers for every tenant. This prints nothing when all is well:

```bash
kubectl get templateinstances.templates.v2.stakater.com mto-argocd-parent \
  -n <operatorNamespace> -o json \
  | jq -r '.status.outputs as $o | $o.ready | keys[] as $k
      | select(($o.ready[$k]|fromjson|join("")) != "True")
      | "\($k): \($o.errors[$k]|fromjson|join(" | "))"'
```

> [!TIP]
> Always use fully-qualified resource names. OpenShift ships its own
> `template.openshift.io/TemplateInstance`, so a bare
> `kubectl get templateinstance` silently returns the wrong kind with an empty
> status — which looks exactly like "the operator isn't reconciling".

### Uninstalling

A plain `helm uninstall` is safe:

```bash
helm uninstall mto-extension-argocd -n <operatorNamespace>
```

The chart's RBAC is kept on uninstall (`helm.sh/resource-policy: keep`, and
`Prune=false,Delete=false` for an ArgoCD-managed release). So
template-operator-v2 still has the permissions its finalizers need while it
reaps the children. What then happens to the AppProjects depends on the
operator version and on purge: see
[What deletes an AppProject](#what-deletes-an-appproject). The NOTES.txt that
`helm install` prints has the commands that remove the kept RBAC.

Reinstalling immediately afterwards fails with an ownership-metadata error —
wait for `Template/mto-argocd-parent` to disappear first.

`tests/e2e` deletes the parent TemplateInstance first, waits for the children
to drain, and then runs `helm uninstall`. That order makes a failed reap show
at the step that failed. The kept RBAC that makes the single command safe is
pinned by the render tests.

## Development

```bash
make test     # helm lint + go vet + render + admission tests
make help     # everything else
```

Four layers, each catching what the one above it structurally cannot:

| Layer | Needs | Catches |
|---|---|---|
| `helm lint` | — | chart structure |
| `tests/render` | — | wrong AppProject content, invariants over random input, scale |
| `tests/admission` | envtest binaries | Template CRs the API server would reject — schema and CEL |
| `tests/e2e` | a cluster (`make e2e-kind` builds one) | what template-operator-v2 does once objects are applied |

**Render tests** execute the chart's gotemplates through template-operator-v2's
*own* function map — `sprig.TxtFuncMap()` minus `env`, `expandenv`,
`getHostByName` — not through Helm, because Helm is not what renders them on
cluster. Helm overrides `fromJson`/`toJson` and adds `toYaml`, `include`, `tpl`
and `.Files`, so a gotemplate can pass under Helm and fail in production.
Mirroring the operator's map makes that class of bug impossible. See
[tests/render/engine.go](tests/render/engine.go).

Fixtures in `tests/fixtures/` are discovered, not enumerated — adding a file is
enough to make it a test. Alongside them, `property_test.go` asserts invariants
over randomly generated clusters, fuzzes the annotation values a tenant
controls, and renders 1000 tenants over about 8000 namespaces, failing above
10 s, to catch an accidentally quadratic filter.

```bash
make helm-render-test-regenerate            # accept an intended output change
RENDER_SEED=1234 go test ./tests/render/... # explore other property inputs
make envtest-assets && make admission-test  # admission layer

make e2e-kind                               # cluster, dependencies, chart, suite
```

**E2E builds its own cluster.** `make e2e-kind` creates a kind cluster, installs
cert-manager, MTO's CRDs, ArgoCD and template-operator-v2, installs the chart
and runs the suite; CI runs the same command on a runner. No credentials —
every component is an anonymous pull, template-operator-v2 included
(`ghcr.io/stakater/public/`). Full instructions in [docs/e2e.md](docs/e2e.md).

There is a second mode for a licensed cluster that already runs MTO, where the
suite *borrows* an existing tenant instead of creating one — MTO's free tier
caps a cluster at two Tenants. Pick one with **no** `Extensions` CR:

```bash
E2E=1 KUBE_CONTEXT=<ctx> E2E_TENANT=<tenant> E2E_ARGO_NAMESPACE=<ns> \
  E2E_OPERATOR_NAMESPACE=<integrationconfig-namespace> make e2e-test
```

`E2E_OPERATOR_NAMESPACE` defaults to the ArgoCD namespace, and the suite reads
the IntegrationConfig from it. See
[docs/e2e.md](docs/e2e.md#running-against-a-real-cluster-instead) before you
run it.

That mode is what proves the chart coexists with MTO; the kind cluster is what
proves the paths MTO's own webhooks make untestable — a privileged namespace
labelled for a tenant, and a tenant with no namespaces at all.

## Differences from the Extensions controller

Deliberate differences from the AppProject the Go controller renders, each
asserted by `TestEquivalenceWithExtensionsController` — which renders with the
compatibility values (`argocd.allowControlPlaneDestination: true`,
`roles.profile: extensionsCompatible`), the configuration a migration starts
from. The secure defaults differ further; `tests/render/security_test.go` pins
them:

| | |
|---|---|
| `metadata` | no `multi-tenant-operator/predicate` label, which MTO puts on the objects it writes; a `templates.v2.stakater.com/deletion-policy: Orphan` annotation when purge is off, which template-operator-v2 reads on teardown |
| `spec.description` | now `Managed by mto-extension-argocd` |
| `roles[].groups` | gains the tenant's **users** alongside its groups. A name listed twice — for example a privileged group that the tenant also lists — appears once, because ArgoCD's API rejects a role with a duplicate group. The same applies to `sourceRepos` |
| `roles[].policies` | one line per project-scoped resource (`applications`, `applicationsets`, `logs`, `exec`, `repositories`, `clusters`) instead of one line with resource `*`. Same access; ArgoCD's API rejects `*` there, so with it every project write through ArgoCD — `create-token`, `delete-token`, the UI — fails. This is the `extensionsCompatible` profile; the default is least privilege, see [Security defaults](#security-defaults) |
| `spec.destinations` | no ArgoCD namespace by default (#6); `argocd.allowControlPlaneDestination: true` restores it, exactly as the controller rendered it |

The users are a fix, not a nicety. The generated group only resolves where
`syncOCPGroups` has run, so a tenant whose owners are users depends on the
user entries for ArgoCD access. Those entries grant access only when
`argocd-rbac-cm` `scopes` includes the claim that carries the user name,
usually `email` — see [Before production](#before-production). With the
default `[groups]` they grant nothing, the same as the old controller's
output. The generated group is still emitted, so nothing is lost where it does
exist.
